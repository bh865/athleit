## 1. What changes, in one paragraph

Today a signed-out person lands on a bare form, email confirmation is one line of text, there is no way to reset a password, errors are the raw backend text, there is no consent line, and the first screen of a new account is four unrelated buttons (add child, create team, create club, join with a code) that lead to separate forms with no sense of what comes next and no sign that a join request is waiting for approval. After this work: mobile opens on a **Welcome** (the social option for the device first, then email, and a quiet "I have an invite or a code"); sign in and create account get a show or hide password, a strength meter, a caps lock hint and a consent line; **Check your email**, **Forgot** and **Reset** are real screens with a Resend cooldown; every error uses the board's copy; arriving from an invite, claim or family link shows a banner saying who invited you and what you are joining before any form; and a person with no place sees an **intent hub** ("What brings you here?") that starts a short path with progress (parent, coach or manager, club, player 13 and over, or "I have a code") ending on a clear next state: a **Pending** card, a **Request sent** screen, or the coach's setup checklist. Web gets the same product as a two-pane desktop layout and a centred card at 834. **Nothing about access changes**: a code never grants access, a guardian or staff member approves, and a pending requester still sees nothing of the team or household.

## 2. Who sees what, and the rules that must not move

Visibility keeps coming from `buildContexts`, `capabilitiesForPlace`, the database and the existing functions, never from this flow. The board's "Who sees what" and flow-map tables in the rules view are a **check**; if they disagree with the code, keep the code's behavior and list each difference in the PR.

- **A code never gives access.** A team code only creates a pending `join_requests` row (`requestToJoin`); staff approve through `decide_join_request`. A family code only creates a pending `household_join_requests` row (`request_to_join_household`); a guardian approves. The onboarding paths call exactly these functions and nothing else. Do not add a client read of teams, households, rosters or people to make a nicer pending screen.
- **A pending requester sees nothing of the team or household.** The Pending card shows only what the requester supplied: the code kind, the child's name they typed, when they sent it, and its status. The team or family name appears **only after approval**, and only through the existing place read. This holds in the UI and in the function in 3b.
- **Children under 13 never have a login.** The parent path adds the child through `addChild` (first name, last name, date of birth, which already creates the household). A date of birth is **never** asked at sign-up, only when adding a child, as today. Players 13 and over claim a login through `claimPlayerLogin` (a claim link) or the player path; a 13 to 17 player's access still depends on a parent, and the `playerWaiting` screen says so.
- **Existing rate limits stay**: family code attempts (`too_many_attempts`), team code lookups, sign-in rate limits in Supabase. Show the limit's own wait time only if the server returns it; otherwise use the board's wording without inventing a number.
- **No account enumeration.** Forgot password always shows the generic "If an account exists for …, we sent a link" wording. Create account may say the email is registered, because Supabase already reveals it and the board draws it, but never on the reset path.
- **Never put a session, token or code in a URL that is logged or shown.** Invite tokens are already in links; do not copy them into analytics, error messages or toasts.

Where the rules view's copy conflicts with `docs/permissions.md` or `docs/registration-privacy.md`, the docs win; list each case.

## 3. Backend and configuration additions (the only backend work), and deviations

Everything else wires to existing functions. Each of these is a migration (or config change) with pgTAP tests in the existing style, RLS on, SECURITY DEFINER only where the neighbouring functions are, `search_path` pinned, grants as in the neighbouring migrations, and a test for each role that matters (the requester, another user, a team staff member, a guardian, a stranger, a signed-out caller where relevant).

**3a. Password reset (no database work; auth configuration and app routes).** `resetPasswordForEmail` with a redirect that lands on a **set-a-new-password** screen, and `updateUser({ password })` there. Needs: `additional_redirect_urls` and `site_url` updated in `supabase/config.toml` and documented in the README's manual setup (hosted project too); a web route (for example `/auth/reset`, added to `PUBLIC_PATHS` only for what it needs, with the code exchange in `auth/callback` keeping its same-site `next` check); a mobile route reached by the `athleit://` scheme **and** the `athleit.app` universal link (add the path prefix to the Android `intentFilters`, and check `associatedDomains` and the apple-app-site-association file the web app serves, if any). Expired or reused links land on `forgotExpired`. After success the person is signed in and goes to Home or the hub. Reuse `changePasswordSchema` and `passwordStrength`. Rate limit comes from `[auth.rate_limit]`; map its error to the board's "Too many attempts" copy.

**3b. Own join requests: read and cancel.** The requester can already `select` their own `join_requests` rows through RLS (check `household_join_requests` has the same policy and add it only if missing), but `teams` and `households` stay hidden to them, so a plain join would fail or leak. Add:
- `get_my_join_requests()` returning the caller's requests (both kinds) with: kind (`team` or `household`), request id, status (`pending`, `approved`, `declined`, `cancelled`), `created_at`, `decided_at`, the child's first name when the request is for a child, and **no team, club or household name unless the status is `approved`**. Order newest first; cap at 20. Declined requests show no reason and no decider.
- `cancel_join_request(p_kind, p_id)`: only the requester's own **pending** request; sets a `cancelled` status (add it to `request_status` and to the household table's check constraint, with the migration touching existing rows and constraints safely), writes the audit entry like `decide_join_request`, returns a friendly error for anything else. Staff and guardians who were notified of the request must no longer see it as pending (check `get_join_requests` and the household equivalent and their tests; update them so a cancelled request disappears from the approver's list).
- Tests: a requester sees only their own rows; another user and staff of another team see none; the function never returns a team name for a non-approved request; cancel by someone else fails; cancel of an approved or declined request fails; the approver's list excludes cancelled requests; a cancelled request can be re-sent through the existing path (the unique pending index still allows it).

**3c. Signed-out invite preview.** Today `preview_invite` is for signed-in callers and the web `/invite/[token]` route is not public, so the invitee sees a generic form before they learn who invited them. Add `preview_invite_public(p_token)` for `anon` and `authenticated`: returns only the **kind** (team, club, family), the **team or club or family display name**, the role being offered, and the inviter's **first name** (the board's banner shows who invited you). Nothing else: no emails, no child names, no member counts, no ids that can be enumerated. Invalid, expired and used tokens return the same shape with an outcome (`invalid` or `expired`) and no detail. Follow the rate-limiting and captcha pattern the public registration functions in `20260301*` already use; if they take a captcha token, say in the plan how the anonymous call gets one without a visible challenge or whether to rate limit only. A claim link gets the same treatment for the player's **first name** only. Tests: anon gets the preview, a used token gives the generic outcome, nothing beyond the listed fields leaks, a rate-limited caller is refused.

**3d. Single code field (the `codeSingle` board, tagged New data).** `identify_code(p_code)` returning only `team`, `household` or `none`, sharing the **same attempt limiter** as `request_to_join_household` and the team code lookup (one counter, not a new free oracle), never any name or count. **Default: ship the two-tab version (`codeTeam`, `codeFamily`) first.** Add the single field only if the function can share the limiter cleanly; otherwise leave `codeSingle` as a marked follow-up and say so in the PR.

**3e. Resend confirmation.** No database work: `auth.resend({ type: 'signup', email })` with the cooldown on the client (60 seconds, from the board; check `[auth.email] max_frequency` and mirror the server's rule, and show the server's refusal as the board's "Too many attempts"). The sign-up redirect (`emailRedirectTo`) keeps going through `auth/callback`. Note that **`enable_confirmations` is false in local config**, so `checkEmail` never appears locally: test it by mocking the `signUp` response (no session returned) and by a separate config run if feasible; say how you tested it.

**Not built** (decide in the plan, do not build): native Sign in with Apple and Face ID (section 6), emailed magic link or code sign-in (the board lists it as optional New data), a Terms or Privacy page (the app already links `NEXT_PUBLIC_TERMS_URL` and `NEXT_PUBLIC_PRIVACY_URL` in the account area: **reuse those variables**, add the mobile equivalents, and when a URL is not set render the consent line as plain text with no dead link; do not write legal text), any change to the public registration flow (`/r/…`, `/register/verify`), which stays exactly as it is.

**Deviations from the board to list in the PR:** every item above built differently from the board; the consent line copy ("You must be 13 or older. Parents create accounts for children under 13.") needs legal review before launch and must not be edited by you beyond the board; **the board's reassurance "Free for families" is marked "confirm before use" in the rules view: leave it out unless Blake confirms**; social buttons that are not enabled for this build (see section 5).

## 4. Flow and data wiring

**Routes.** Keep every existing URL working: `/sign-in`, `/sign-up`, `/auth/callback`, `/invite/[token]`, `/claim/[playerId]`, `/join`, `/family/children/new`, `/teams/new`, clubs creation, `/r/…`, and the mobile equivalents. Other screens link to them. New routes (names are yours to propose in the plan): check-email, forgot, reset, and the onboarding hub and its steps. The hub renders where the Welcome renders today (`(app)/page.tsx` on web, `(app)/index.tsx` on mobile) **when the person has no place and no pending request**; the Pending card replaces it when one exists.

**Sign in and create account.** Wire the existing `signIn`, `signUp` (with `display_name`) and social buttons to the new screens. Keep `signInSchema` and `signUpSchema`. **Keep the web form labels `Your name`, `Email` and `Password` exactly**, because the e2e helpers sign up and in by label, and keep `?next=` and `PENDING_INVITE_KEY` behavior. Password field: show or hide as a labelled toggle, caps lock hint, strength meter with the words ("Password strength: Strong"), minimum 8 from the schema. `signUp` returning no session means "check your email": navigate to `checkEmail` with the address shown, Open mail (deep link to the mail app on mobile where the platform allows, no dependency added for it), Resend with the cooldown, and Change email. When the confirmation link is opened on the same device the screen continues by itself (`checkEmailDone`): listen to the auth state change and also handle the case where the link opens in the browser instead of the app.

**Errors.** One core function maps Supabase and network errors to the board's copy table (wrong password or unknown email, email in use, registered with Google or Apple, weak password, too many attempts, no connection, server problem, link expired, social cancelled). Extend `errors.ts` / `friendlyError`; never show the raw backend text; unit test every row. The copy for "registered with Google" must only appear when the app can truly tell (the provider list); otherwise use the generic mismatch copy, and say which in the plan.

**Link arrival.** The banner and Continue as come from `preview_invite_public` (3c) when signed out and from `previewInvite` when signed in. Signed-out: banner, then Create account or Sign in, the token kept through sign-up and OAuth (mobile `PENDING_INVITE_KEY`; web `next`), then `acceptInvite` (or `claimPlayerLogin`) and the existing landing confirms. Signed-in on a different account than the link's: **Continue as** shows the current account and offers Switch account, never acts silently. Invalid and expired links use the board screens and offer "I have a code" and Create account.

**Hub and paths** (what each ends with, and which function it calls):

| Intent card | Steps | Calls | Ends on |
|---|---|---|---|
| I'm a parent | Add your child (repeatable with "Add another") → "Is {first name} on a team?" → team code → Request sent | `addChild`, then `requestToJoin` per child | Request sent, then the Pending card on Home |
| I coach or manage a team | Create your team (name, sport, optional club) → Invite your families (link, code, QR, share) → optional first event (collapsed) → You're set | `createTeam`, optional `findClub` and join-club flow already used by team creation, the existing invite, code and QR components, the existing create-event function | Checklist; Home shows the setup state through `next-up-state.ts` |
| I run a club | Create the club (name and address, taken-address state) → Bring your teams → set | `findClub`, `createClub` | Club set; teams ask to join and approvals appear on Home |
| I'm a player (13+) | Link my login | `claimPlayerLogin` (claim link) or the player path | `playerLinked` or `playerWaiting` |
| I have a code or invite | Team code tab, Family code tab (single field if 3d ships) | `requestToJoin`, `request_to_join_household` with its four outcomes | Request sent |

The board's copy for each outcome comes from the rules view. **The hub never creates anything by itself**; each path's last step is the one that calls the function.

**Hub variants.** `hub` for a person with no history; `hubReturning` (quieter, with "Rejoin or join") when the person has had any join request or has completed the hub before. Detect "returning" from `get_my_join_requests` (3b) **or** a local flag set when the hub path completes (`lib/kv.ts` on mobile, a cookie or local storage on web); **no new server field**. Skip, "Not now", and a way back to the hub from Account must exist so nobody is stuck; the hub is not a gate when the person has a place.

**Pending card (`pendingHome` and siblings).** Reads `get_my_join_requests`; Cancel request opens `pendingCancelSheet` and calls `cancel_join_request`; Approved shows the place once the place read returns it (no extra read) and offers Open; Declined and Cancelled are calm states with a way to try another code. Reload on the existing realtime or notification signal and when the app returns to the foreground.

**Notifications soft-ask (`notif`).** Shown once, after the person's **first approved place**, not at sign-up, through `lib/push.ts` and `registerPushDevice`; "Not now" is remembered locally; permission text states the plain reason (approvals, schedule changes, messages). On web, no browser prompt is added.

**Shared logic in `packages/core`, unit-tested with an injected clock where time matters:** the error-to-copy mapper; password strength words; resend cooldown; the intent-to-path table and the step counter ("Step 2 of 3"); returning-hub detection; the pending-request view model (status wording, what may be shown per status); code kind detection (a client-side format check only, never "this code exists"); invite banner copy by kind and role; consent line composition (with or without links). Extend existing files rather than creating parallel ones.
